## What Harvester is

A Rust + gpui desktop app that orchestrates **Pi** coding-agent sessions on remote machines. Sessions run detached on the machines — the client is a window onto them, not their owner. Close the laptop, the agents keep working; reopen it, everything is still there.

**Scope (locked):** Pi is the only harness. exe.dev is the only built-in infra target (its VMs are always-on). Other platforms are reachable through the provider contract, not through built-in integrations.

## Architecture

```
┌──────────────┐   SSH (socket forward)   ┌────────────────┐   stdin/stdout   ┌────────────────┐
│ gpui client  │ ───────────────────────► │  harvesterd    │ ───────────────► │ pi --mode rpc  │ × N sessions
│  (desktop)   │ ◄─────────────────────── │  (per machine) │ ◄─────────────── │  (per session) │
└──────────────┘                          └────────────────┘                  └────────────────┘
       │                                          │                                  │
       │ one-shot exec                            │ spawns/reaps                     │ appends
       ▼                                          ▼                                  ▼
┌──────────────┐                          in-memory only:                    ~/.pi/agent/sessions/
│  providers   │                          pid table, stdin                   <cwd>/<ts>_<sid>.jsonl
│ (~/.harvester│                          handles, attached                  (the ONLY source of truth)
│  /providers) │                          clients
└──────────────┘
```

Design invariants:

- **Disk on the machine is the source of truth.** Pi's own session files (documented, versioned v3, durable `get_entries {since}` cursor) are the persistence layer. harvesterd persists nothing; the client caches nothing authoritative. A client *may* hold a **repairable, evictable transcript replica** keyed by a pi entry-id cursor — fetch once, extend with `get_entries {since}` — because repair is always available: drop the cursor and refetch. What stays forbidden: the replica is never the answer to "what happened" (any doubt is resolved by refetching, never by reconciling), it never outlives the process that holds it (in-memory, evictable at any time — closing a session may discard it), and a cursor pi rejects (`Entry not found: <since>`, source-verified in `rpc-mode.js`) means refetch from scratch. The session file on the machine remains the only authority.
  - *Built.* The bridge holds the cursor (pi's `leafId`, tagged with the sid it came from, so it cannot be spent on the session that replaced it); the frontend's `Transcript` holds the replica and records how much of it pi confirmed. A repair sends `get_entries {since}` and extends; a delta that fails for any reason falls back to a full refetch, which covers the retired-cursor case without matching on pi's error text. **Live events carry no entry ids**, so items built from them are dropped before a delta is applied — the delta is the authoritative account of the very span they were guessing at.
- **Each layer dies and recovers independently.** Client crash → sessions unaffected. harvesterd crash/upgrade → pi children exit, state is on disk, resume is one call. pi crash → session file survives, `session_exit` event, resume-or-create relaunch.
- **The client speaks Pi.** No normalized event model, no translation layer. Pi RPC commands and events pass through harvesterd verbatim inside a thin envelope.
- **Multiple clients are first-class.** Desktop and (future) mobile can attach to the same session simultaneously; events broadcast, state recovers via the durable cursor.

## Citizens

### Machine

Where agents run. Keyed `<provider>/<id>` (e.g. `exe-dev/bloggy`). Two kinds:

- **local** — hardcoded, read-only, never deletable. The client spawns harvesterd as a child process and talks over the Unix socket directly, no SSH.
- **provider machines** — enumerated by provider executables in `~/.harvester/providers/` (see `PROVIDERS.md`). Providers answer *what machines exist and how do I SSH into them* plus create/delete; they are control-plane only. Session traffic always flows over plain SSH using the returned connection info (`{host, user, port}` or the `{argv: [...]}` ProxyCommand-style escape hatch).

Harvester ships one default provider, `exe-dev` — a thin wrapper over exe.dev's SSH control plane (`ssh exe.dev ls|new|rm --json`), implemented in the same format as user providers. No privileged code paths.

**Status dot**: the machine row's whole story — rows carry no link-state text, only the machine's source (`exe-dev`, `ssh`; `local` has no subtitle). Green = daemon connected (a live bridge is proof, no probe needed); yellow = bridge connecting/bootstrapping; red = connect failed/lost, Harvester's own probe (`ssh <machine> true`, 30s cadence; provider `list` polls at 300s) says unreachable, or the machine is **gone from its provider's listing**; filled gray = probed reachable, nothing has connected yet; **hollow gray = nothing is known at all** — never probed, never connected. Never provider-reported status (advisory only). `local` follows the same mapping — hollow until its daemon is spawned.

Three sources speak into that one dot, and they rank: a live bridge outranks everything (we are talking to the machine, whatever its provider says), the *listing* outranks a probe verdict (a probe answer for a deleted machine is stale by construction), and a probe outranks nothing at all. **A tracked machine its provider no longer lists gets a row anyway**, marked *no longer listed* — the machines section is the listing plus those ghosts, because a machine that appears nowhere while a workspace still points at it is how the client comes to sit idle with no explanation. A ghost row is also **the one machine row that can be acted on**: it carries a trash button that forgets the machine (§Flows "Forget machine"). Every other machine row stays read-only — it is still listed, so there is nothing to clean up and nothing Harvester can be sure is gone. A provider that has *never* listed successfully says nothing about its machines: absence is only evidence once that provider has reported, or one broken control plane would declare its whole fleet deleted.

**Harness readiness is specified, not implemented.** The design answer — does this machine have a working pi? — is `pi --version` + `pi auth print-bearer-token --model <m>` (never `--list-models`, which exits 0 with no models). Nothing runs it: the only probe in the client is `ssh <machine> true`, so a reachable machine with no pi, or with pi but no credentials, is indistinguishable from a healthy one until a session fails to start.

The client also carries **ad-hoc machines** — plain SSH destination strings (the argv launch form, legacy workspaces.json entries) used verbatim, keyed by the string itself. They probe and connect like provider machines; they just come from nowhere but the user.

### Workspace

A git repo on a machine, stored as `machine → path`, displayed as `folder_name in machine_label`. Validation and browsing are plain SSH execs by the client (`ls -1Ap`, `git -C <path> rev-parse --git-dir`) — no daemon or provider involvement. Every SSH exec **the client itself** makes multiplexes via `ControlMaster=auto` (`ControlPersist=60`), so a per-click listing skips the handshake and costs about one network round trip (measured on exe.dev: ~1.7s cold → ~0.35s multiplexed); `auto` degrades to a plain connection if the master is unusable. The control socket lives in **`~/.harvester/run`, mode 0700** — never the temp dir: a predictable path in a world-writable directory can be squatted before we bind, and ssh's mux protocol is unauthenticated, so a fake mux server would MITM every exec (the temp dir is used only as a loud fallback when `$HOME` is unusable). Same reasoning as the daemon's socket dir; see `DAEMON.md` §Transport.

The claim stops at the client's own execs. **Providers are separate programs and build their own ssh command lines** — the bundled `exe-dev` sets neither `ControlMaster` nor keepalives, so each 300s `list` cycle pays a cold handshake. That is correct per `PROVIDERS.md`, not an oversight: what a provider does with its control plane is its business, and Harvester cannot multiplex a connection it does not make. The picker starts at the machine's `$HOME`, read by a one-shot exec (`printf '%s\n' "$HOME"`) when the picker opens. All three ops run on the machines worker, keyed by `Host` and correlated by request token — the picker never touches a machine's daemon, so browsing a machine Harvester has never bootstrapped costs one round trip, not an install.

The workspace list lives client-side in `~/.harvester/workspaces.json` (plain JSON, `[{machine, path}]`). This is user configuration, not session state — the "client caches nothing authoritative" rule is about session data, whose truth stays on the VM's disk. It is **the repo picker's backing store and nothing else**: a workspace is not a citizen with a list of its own, it is the set of repositories the chat's repository dropdown offers for a machine. Adding one is a side effect of picking a repo Harvester had not been told about; there is no *per-repository* removal UI (a stale entry costs one wrong row and is a file the user can edit). The one removal that exists is per machine, and it is a machine removal rather than a repo one: forgetting a machine deletes all of its entries at once (§Flows "Forget machine"). That works because this file is the only place a machine is persisted — the tracked set, the machine's sidebar row and its session rows are all derived from it, so one write is the whole deletion.

A repo also carries a **branch**, read but never written: `git -C <path> rev-parse --abbrev-ref HEAD` over the same client-side exec path, for the chat prompt strip's read-only indicator. Pi manages branches and worktrees itself, so Harvester has no branch picker and no branch state — the indicator is refetched when a repo is picked and after each settled turn, and shows nothing at all when the exec fails.

### Session

A running (or resumable) `pi --mode rpc` process in a workspace, owned by that machine's harvesterd. Session id = client-generated **uuidv7** (pi's own native id format). One pi process = one session file, always — the session-swapping pi commands (`new_session`, `switch_session`, `fork`, `clone`) are never sent.

The full lifecycle, launch line, envelope, and event semantics are normative in `DAEMON.md`. Summary:

- **Launch**: `PI_OFFLINE=1 GIT_TERMINAL_PROMPT=0 GIT_SSH_COMMAND="ssh -o BatchMode=yes ..." pi --mode rpc --session-id <sid> --approve [--provider --model --name]`, cwd = workspace, stderr → `~/.harvester/log/<sid>.stderr.log`. `--approve` loads project `.pi/` resources (user's repo, user's call); the git env guards convert would-be credential hangs into fast failures.
- **Resume = create**: same call, same sid (`--session-id` is resume-or-create, source-verified).
- **Stop**: close stdin (never SIGTERM), 30s backstop, SIGKILL, reap.
- **Rename**: pi's `set_session_name` — persisted as a `session_info` entry in the session file itself.
- **List**: readdir pi's per-cwd session dirs; header line + last `session_info` entry; `running` if pid alive in daemon table, else `exited`.
- **Reconnect**: attach → `get_entries {since: last-seen-entry-id}` → live events. Deltas are never replayed. An *open* still fetches the whole session — there is no replica to repair when the chat is being created — but every `event_gap` resync after it costs only the entries since the last fetch.

## UI

### Layout

```
{sidebar} {sessions_tabs}
{sidebar} {chat}
{sidebar} {statusbar}
```

Sidebar: `new_session_button`, `machines_header/list`, `sessions_header/list`. Both section headers are collapse toggles (trailing chevron); the New session button is the sidebar's main action, and it is always enabled — where a session runs is picked inside the chat it opens, so there is nothing to choose here first. The sidebar's only other action is the trash button on a *no longer listed* machine row (§Flows "Forget machine"); every other machine row is listed, not clicked. Session rows always subtitle `workspace · machine` and navigate by sid — the list is a filtered view: remote machines show every session their daemon lists (the VM's disk is the only source of truth, nothing client-side to scope by), while the `local` machine's sessions are scoped to added workspaces (its daemon would otherwise surface every repo this computer ever ran pi in; the unfiltered list stays in memory, so adding a workspace reveals its sessions without a refetch).

### Rendering pi

The chat renders pi's event stream directly:

- Streaming text/thinking: `message_update` deltas (each carries the whole partial message — replace, don't append).
- Tool calls: `tool_execution_start/update/end` correlated by `toolCallId`; updates carry accumulated snapshots (replace the block). Pi runs tool executions in parallel — several `start`s can precede their `end`s, and ends arrive out of order (verified live, pi 0.83.0). The assistant `message_end` precedes its tool executions, so push order is render order. Edit results carry a pre-rendered numbered diff in `details.diff` (`" 1 ctx" / "-2 old" / "+2 new"` lines); `toolResult` history messages carry the same fields, so replayed blocks equal live ones.
- Turn done: `agent_settled` (not `agent_end` — retries/compaction/queued follow-ups may still run after `agent_end`).
- **Turn failed: the assistant `message_end` itself.** Pi reports a failed or aborted turn as an assistant message whose text is the *empty string*, with the reason in `errorMessage` / `stopReason` (pi 0.83.0 `pi-agent-core/dist/agent.js`) — and persists it to the session file. A transcript that renders only non-empty text therefore drops the whole turn, which is what made an expired provider token look like a prompt nobody had sent. `Transcript` reads the reason out as `Item::Failure`, live and on replay, and the chat renders it authored "pi" in the failed tone and without markdown.
- Busy states: `compaction_start/end`, `auto_retry_start/end`, `queue_update` → statusbar.
- Cost/tokens: `get_session_stats` → statusbar.

Extension dialogs map to native modals: `select` → list, `confirm` → yes/no, `input` → text field, `editor` → multiline; `notify`/`setStatus` → toast/statusbar. All payloads are plain data — pi disables TUI-only UI in RPC mode, so nothing unmappable can arrive.

### Flows

**Add machine** (deferred to the machine-CRUD slice) — "+" in machines_header → provider picker (from discovered providers advertising `create`) → modal generated from the provider's `create_fields` → provider `create` → connectivity assert (`ssh <machine> true`) → store.

**Forget machine** — trash button on a *no longer listed* machine row → confirmation dialog (`Remove machine <label>?`, naming how many of its sessions leave the list, and that nothing on the machine itself is deleted) → **every entry for that machine leaves `workspaces.json`**, in one atomic rewrite. That single write is the whole removal, and everything else falls out of it by derivation: the tracked set is recomputed from the file, the fleet drops the now-untracked machine (dropping its bridge handle with it), the ghost row goes with the tracked set that produced it, and the machine's session rows — display state from a daemon this client will never reach again — go with the machine. A chat still pointed at it closes for the same reason. A failed write forgets nothing and says so in a notification. Only ghost rows offer this: a machine its provider still lists is not the user's to clean up here, and its sessions are still real. Deleting an individual *session* is a separate feature for *reachable* machines, and is not built.

**Add repository** — "Add new…" in an unstarted chat's repository dropdown → folder picker on the machine that chat already targets (`ls` walk starting at its `$HOME`, both plain host execs — no bridge, so nothing to wait for beyond the exec itself) → `git rev-parse` validation (clear error in the modal, re-pick on failure) → store as `{machine key, path}` → the asking chat selects it. There is no machine-choice step: the chat has a machine before its repo dropdown opens.

**Start session** — the sidebar's New session button opens a chat with no session behind it yet, titled "New session". This is **the same chat component** a live session uses, in an earlier state — not a separate "ghost" surface. The prompt box carries flat controls in its bottom row (agent-input pattern, each an icon and its label a `gap_4` apart: `model · machine · repository · branch`): the model control (an in-place dropdown fed by daemon `list_models`: throwaway `pi --no-session` answering `get_available_models`, fetched when the chat opens and again whenever the cwd or the machine changes; thinking-level picker deferred), a machine control listing **every reachable machine**, a repository control listing that machine's stored repos plus "Add new…" below a divider, and the read-only branch indicator. Picking a machine retargets the chat (lazy bridge connect) and carries the repo with it — a stored path belongs to a machine — so the new machine's first repo is selected, or none when it has none.

The chat opens **pre-picked**: the machine and repo of the most recent session that is still a stored repo on a reachable machine, else the first stored repo, else the first machine with no repo. That default is *derived at open time and never persisted* — a guess that survives restarts is a preference nobody agreed to keep. Until both halves resolve the send button is disabled and the state machine refuses the prompt, which is also the whole of the empty-fleet story: New session always opens, the machine control reads *no machines*, the repo dropdown offers only "Add new…", and that path is the onboarding. On first prompt: generate uuidv7 sid → `create_session` on the picked machine's bridge (with `name` derived from the prompt itself: first line, truncated) → attach → `prompt`. No readiness probe — pi's stdin queue drains in order (verified, `HARNESS_RESEARCH.md` §Round 4), so commands chained right after `create_session` are safe.

The three states are `unstarted → starting → live`, and they are one-way. What differs between them is small and worth naming: whether the machine and the repository can still be picked (only unstarted — the launch line is `cd <repo> && pi`, and pi's cwd and host are fixed for its lifetime, so a running session never moves), and what a model pick *means* (a launch-line argument, versus a `set_model` the running pi must confirm). Everything else — the pane, the prompt box, the input, the model control — is shared, which is why they are one component. The user's first prompt renders immediately and the chat is promoted in place when `Attached` lands; it is never rebuilt, for the same reason a resync does not rebuild it (C7).

**Switch model (live session)** — the attached chat's prompt box shows the session's current model (passthrough `get_state`, fetched at open together with passthrough `get_available_models` — both are milliseconds against the running pi, no throwaway process). Picking from the same in-place dropdown sends passthrough `set_model {provider, modelId}`; on success pi returns the Model now in effect and the label updates (no optimistic update), on failure the statusbar shows pi's error and the session keeps its model. The live picker has no "default" row — a running session always has a concrete model.

**Rename session** — right-click → Rename → inline input → Enter → passthrough `set_session_name`.

**Resume session** — click an `exited` session → `create_session` with the same sid → attach → `get_entries` renders history.

**Reopen client** — machines with stored workspaces connect in the background at startup (each: connect, `ping` — re-bootstrap harvesterd on version mismatch — then `list_sessions`); every other machine connects lazily on first touch, and a failed or lost bridge respawns on the next touch. Re-attach to whatever the user opens. Nothing was lost because nothing lived in the client.

## Auth & model routing (machine-side)

- Pi resolves credentials as: `--api-key` > `~/.pi/agent/auth.json` > env vars > `models.json` keys. auth.json outranks env vars — beware stale baked-in files.
- **exe.dev VMs: keyless, VERIFIED end-to-end (smoke test 2026-08-01).** The image ships a pi extension (`~/.pi/agent/extensions/exe-dev`) that discovers the VM's LLM-gateway models and registers them in pi (full Claude/GPT/grok/deepseek/kimi catalog, `*@llm` ids, cost metadata included). No keys, no `models.json`. Enabling it takes a pre-seeded `~/.pi/agent/exe-dev-llm-integration.json` = `{"version":1,"useExeIntegration":true}` (otherwise the extension pops a startup `select` dialog and, unanswered, silently skips the integration). **Implemented in the `exe-dev` provider's `create`** (`seed_llm_integration`) — the provider is the one citizen that knows a machine is an exe.dev VM; the daemon bootstrap must never do it, since its start script also runs for `local` and would write into the user's own `~/.pi`. Idempotent and non-destructive: an existing file is left exactly as it is (and logged when it does not enable the integration), and a seed that cannot reach a still-booting VM is a stderr diagnostic, not a `create` failure. **Scope**: it runs when Harvester creates the VM, so VMs created outside Harvester (including every VM that predates this) still need the file seeded by hand. **UNVERIFIED against a live VM.**
- Fallback for non-exe.dev machines: user's own keys via env or auth.json.

## Non-goals (v1)

- Other harnesses (Claude Code, Codex) — cut.
- Built-in platform integrations beyond exe.dev — the provider contract is the extension point.
- Approval/permission system, Harvester-shipped pi extensions.
- Event normalization, daemon-side journaling, session metadata files.
- Machine mutation (resize/rename), provider push/events, provider health ops.
- Windows (provider discovery relies on the executable bit) — Linux/macOS first.

## Post-v1 ideas (on record, not designed)

- **TypeScript SDK** (`import { provider } from "harvester"`): pre-built APIs to compile spec-compliant provider binaries; derives `capabilities` from supplied handlers. SDK = convenience, stdio contract = spec.
- **Update dependencies** button per machine: `ssh <machine> 'exeuntu update pi && pi update --all'` (`pi update` never prompts for trust). No daemon involvement.
- **Mobile client**: protocol already supports it (multi-client attach + durable cursor); needs only an SSH transport lib.
- Per-workspace trust toggle if `--approve`-by-default ever needs opting out.
- Shared-machine socket auth (token in `ping`) if machines stop being single-user.
- **A docked, tabbed workbench** (`gpui-component`'s `DockArea`): several chats open at once as tab panels, a drag-resizable sidebar in place of the hardcoded 240px, and a layout the user rearranges and we serialize. Deferred deliberately — it is a pure layout change once C12 has made a chat keyable by sid, and doing it earlier would mean designing the shell twice.
- **Pi protocol v2 watch**: upstream is incubating a binary CBOR client↔server protocol (bearer-token hello, authoritative snapshots). If pi ships a server mode, harvesterd shrinks toward a bootstrapper; our pass-through design keeps the client's rendering untouched (`HARNESS_RESEARCH.md` §Watch).

## Decisions on record

Settled in the 2026-08-04 backend review, plus the hardening pass that followed it. Each says whether it is built; they are here so the next round starts from the verdict, not from the argument.

- **C2 — worker replies correlate by a monotonic token** (`RequestToken`, minted from one process-wide `RequestTokens`), carried on every command that has an answer and echoed on that answer, replacing the per-command echo-key staleness guards (`cwd`/`path`): those were ad hoc per command and could not tell two in-flight requests with the same key apart. *Built.* Scope as built: commands with no reply (`Open`, `StartSession`, `Prompt`) carry no token — what they produce is the session's own event stream, keyed by sid — and a session-scoped answer still carries its `sid` as *routing* (which chat renders it) alongside the token that correlates it. Every session-scoped pi command now rides one generic round trip (`Command::PiRequest { sid, cmd, token }` → `Event::PiAnswered { sid, token, method, result }`) rather than a typed command-and-event pair per pi verb, so `cmd` stays verbatim Pi — the client speaks Pi — and a new pi verb costs no backbone code; `method` is that command's own `type` echoed back, which is what lets a consumer that is *not* the asking control — the statusbar reporting a refused `set_model` even after its chat closed — recognize the answer without re-typing the command.
- **C3 — the full `Fleet` extraction out of `workbench.rs`**: bridge pool, machine table, probe verdicts, connect policy and machine identity move into client-core behind one owner. The gpui crate is headed for dumb, stateless components, so decomposing `workbench.rs` is a prerequisite, not speculation. *Built* (`client-core/src/fleet.rs`): one `MachineState` per machine replaces the `connections`/`probes` pair, so a probe verdict can no longer contradict a daemon link; `FleetError` carries the human-readable failure reason the statusbar shows, verbatim; every method is synchronous, so gpui's reactor-free executor is never asked to await a tokio primitive.
- **C7 — a repair is not an open.** `bridge::Event::Attached` meant both "you opened this session" and "here is the snapshot repairing what you missed", and the gpui frontend rebuilds the chat entity on every one — so a resync landing after the user had scrolled or typed clobbered the chat on screen. The two are separate events now: `Attached` (create the chat for `sid`; `entries` is pi's list verbatim, empty for a brand-new session) and `HistoryReplaced` (replace an existing chat's entries; ignore it if there is no chat for `sid`). Both carry the same `get_entries` payload — the difference is entirely what a frontend is licensed to do with it. *Built, both halves.* C6 added a third, `HistoryExtended`, under the same rule — a cheaper repair, licensed the same way.
- **C8 — a resync is scoped and deduplicated.** Every daemon `event_gap` used to spawn a full `get_entries`, with `attached` never consulted and no in-flight check: a gap for a session nobody was watching cost a refetch, and N gaps cost N concurrent refetches of one history. The bridge now repairs only the session it is attached to, and only one repair per session at a time (the attach-window overflow retry is a loop under the same claim). *Built.*
- **C9 — an attachment does not outlive its pi.** `BridgeContext.attached` was cleared only by `detach_previous`, so a session whose pi exited stayed recorded and the next `Open` sent a `Detach` for a dead sid — surfacing to the user as a statusbar error for an action they never took. `SessionExit` forgets it, scoped to the sid that exited. *Built.*
- **C6 — clients may keep a repairable transcript replica** (the amendment in Design invariants above), and `get_entries {since}` is implemented properly instead of an always-full refetch. *Built.* The cursor and the replica are owned separately on purpose: the bridge makes the calls, so it holds pi's `leafId`; the frontend holds the items, so it holds the boundary between what pi confirmed and what live events guessed. Neither needs the other's half, and the pairing of cursor-to-sid makes a cursor from a replaced session unusable rather than merely unlikely.

- **C10 — the ghost chat and the live chat are one component.** They were two — `workbench/ghost.rs` and `chat.rs` — each owning an input, a subscription, a focus flag, a model control and a copy of the prompt box, with the workbench arbitrating which one's modal was open in three separate places. Everything the user touches is the same on both sides of the line; what differs is named in the state (`unstarted / starting / live`) and is two facts wide. Folding them removed the duplicate prompt box, the duplicate model-control plumbing, the `GhostRequest` enum and its hand-carried `Command`, and the "whose picker is this?" precedence — and made the first prompt render immediately instead of blanking the pane until `Attached`. *Built.* The workbench now holds one `Option<Entity<Chat>>` and routes to it; `ghost.rs` is deleted.

- **C11 — the client's widgets come from `gpui-component`, tracked at `main`, not at a release.** `crates/harvester` hand-rolls its entire widget layer: a 651-line text input vendored from gpui's example (IME, grapheme cursor movement, a bespoke `Element` that shapes and paints the line), a 30-constant dark-only palette, and `ui.rs` — buttons, rows, scrims, modal frames, tool blocks — with `kitchen.rs` existing only to preview them. None of it is the product. `gpui-component` supplies all of it plus what we never wrote: virtualized lists, real scrollbars, focus traps, ESC-dismissable dialogs, notifications with a lifecycle, and a markdown view with tree-sitter code blocks for the transcript. *Built* — the window root, the prompt input, every modal, every list row, the transcript's markdown and the palette have all landed.

  **Why `main` and not the crates.io release.** `gpui-component 0.5.1` (2026-02-05) depends on crates.io `gpui 0.2.2` — an exact match for our current pin, and the reason this looked like the safe choice. It is not. Sixteen days after that tag, upstream moved to Zed's split `gpui` + `gpui_platform` crates, and **`gpui_platform` has never been published** — crates.io answers *"crate `gpui_platform` does not exist"*. Cargo refuses to publish a crate carrying a git dependency, so longbridge *cannot* cut another release until Zed publishes gpui again, and Zed has published nothing since `0.2.2` (2025-10-22). `0.5.1` is therefore not a stable release to sit on; it is a frozen branch 517 commits behind that nothing will ever supersede, whose bugs will never be fixed, and whose published documentation describes `main` rather than itself (`Table` vs `DataTable`, `divider` vs `separator`, a stale `Root::render_dialog_layer` signature). The features that decide this migration are `main`-only: `TextViewState::push_str` gives incremental markdown reparse — exactly the streaming pi transcript — where `0.5.1` re-parses the whole document each debounce tick.

  **What it costs.** Git dependencies on the zed monorepo for both `gpui` and `gpui_platform`, with gpui built from source, and `Application::new()` becomes `gpui_platform::application()`. The manifests intentionally name the Zed git repository without `rev`; this workspace's `Cargo.lock` is the pin and currently resolves both crates to `08827f9208b4848d62f3faf86ffa15155966d63c`. `gpui-component` and its assets are separately rev-pinned at `f96f1576`. Bumps are deliberate `cargo update`s, never incidental resolution during a locked build. The musl constraint does not apply — only `harvesterd` targets musl; the client is an ordinary desktop binary, and gpui stays quarantined to `crates/harvester` exactly as before.

  **What it obliges.** Three things are not optional: `gpui_component::init(cx)` before anything else (it installs the theme global and binds keys for the input, table, list and menu contexts — our 15 `TextInput`-scoped bindings are deleted, not reconciled); `Root::new` as the window's first-level child, with the dialog, sheet and notification layers rendered by our root view, or `open_dialog` silently does nothing; and an `AssetSource` (`gpui-component-assets`), without which every icon renders blank. No default features are enabled — syntax highlighting is opted into per language, and we take `tree-sitter-typescript`, `tree-sitter-tsx` and `tree-sitter-bash` (json arrives free with the base `tree-sitter` feature), because clean-build time is the real cost of the other thirty-two grammars.

  **Scope.** Roughly 1,700 lines deleted: `input.rs` entire, with the `unicode-segmentation` dependency and the keybinding block; `theme.rs`'s thirty hex constants for the library's ~180 semantic tokens, `Tone` collapsing onto `danger`/`success`/`warning`/`muted_foreground`; `ui.rs`'s scrim/modal/button/row helpers; most of `kitchen.rs`. The library's own dark theme is adopted rather than the current palette being ported onto it — a deliberate call that the app may look different, taken because the palette is not the product. Harvester stays dark-only: `theme::init` hardcodes `ThemeMode::Light`, so `Theme::change(ThemeMode::Dark, …)` follows it explicitly, and `Theme::sync_system_appearance` is never called — nothing else in the library observes system appearance, so a light-mode desktop cannot drag the window light. The `harvester-client-core` seam — `Fleet`, two mpsc receivers, `Transcript` — does not move. Sequenced deliberately: bootstrap, input, dialogs, then C12, then lists, then the transcript, and `theme.rs` and `kitchen.rs` deleted last. The palette is *not* converted up front, which was the original plan and was wrong: `ui.rs`'s helpers are free functions with no `&App`, so moving them onto `cx.theme()` means threading a context through several hundred call sites that the dialog and list steps then delete. Each component instead picks up the theme as it is migrated, and `theme.rs` dies when its last reference does — at the cost of two palettes coexisting mid-migration. The input step is the first to pay a structural cost rather than a mechanical one: `InputState::new` needs a `&mut Window`, and a `Chat` is created inside mpsc event handlers that have only a `Context`, so the pumps become `spawn_in`/`update_in` and `window` is threaded down through `handle_bridge_event` to both `Chat` constructors. That is one atomic change — it cannot land half-done. **The dialogs-as-modals slice lands inside this migration, not before it** — building it against `ui.rs::modal_frame` first would be work thrown away within a step. A throwaway spike gated the decision, and **it passes**: against `gpui-component` at `f96f1576`, a clean build takes 2m33s wall for 853 crates, and a chat-shaped smoke — prompt input, streamed markdown transcript, dialog, notification, icon — compiles and links. The one surprise justifies the pin discipline above rather than undermining it: declaring the zed dependency unpinned, as upstream does, resolved to `08827f92` and not the `4aad57fd` their lockfile records, because a dependency's lockfile is ignored. It built anyway, so the rev we hold is ours to choose and ours to move — deliberately, via our own lockfile.

  **`Sidebar` is not ours to use; `ListItem` and `List` are.** The plan named three library pieces for the list step — `ListDelegate`, `Sidebar`, `Select`. `Sidebar` was dropped after reading it: `SidebarMenuItem` is one line of text (`label: SharedString`, an optional icon, a right-hand `suffix`), and §UI locks *"session rows always subtitle `workspace · machine`"* while a machine row carries a provider subtitle beside its dot. `Sidebar<E>` is also generic over a *single* item type, and `SidebarGroup`'s label is not a click target — so per-section collapse is not in there either. Adopting it costs two locked UI decisions and buys a container. `Collapsible` is a bare show/hide wrapper with no header, chevron or click, and replaces nothing.

  What does fit is one layer down. `ListItem` is a `ParentElement` over `h_flex().id(…)` with `selected`/`disabled`/`suffix`/`check_icon`, so a two-line row is just its child: every `*_row` helper in `ui.rs` became one, and the hand-rolled hover, selection and check-column went with them. `disabled` turned out to be the honest word for the read-only rows — a machine row is listed, not clicked, so no hover and no pointer is the correct affordance, and the dot stays the row's whole signal (§UI machine dots). `List` + `ListDelegate` took the modal lists, which is where virtualization is real: a home directory has no bound. (The model list has since left the modals for an in-place dropdown — see below — and the add-workspace machine step has since been deleted with the workspaces section, so what remains virtualized is the folder picker.) Note the split the library draws and we adopted: `selected` is the list's own cursor (it overrides whatever an item says), `confirmed` is "this is the one in effect" — which is what the model picker's check mark actually means.

  The folder picker paid for this with a split worth having. `Walk` is where the picker is, what it is waiting on and what a click decides — no window, no entities, and the ten tests in that file drive it end to end; `FolderPicker` is the view holding the walk and its list. `Walk::accept_listing` hands its entries *back* rather than storing them, so the walk keeps no copy of what is only ever rendered, and `open_dir` takes a name rather than an index into a listing it no longer has.

  **The palette dies last, and `Tone` outlives it.** `theme.rs` and `kitchen.rs` died with the migration's last step: thirty hex constants and the 579-line catalog that existed to preview them. Every surviving visual helper takes `&App` and reads `cx.theme()` — the cost the sequencing was chosen to avoid, paid last, when the call sites left to thread are the ones that survived rather than the several hundred the dialog and list steps deleted. What did *not* die is `Tone`: it now lives in `ui/core.rs`, because the argument that put it at the visual seam is untouched by where the colours come from. A component handed `cx.theme().success` has had a theme decision made for it by its caller and can never be re-themed; one handed `Tone::Live` has not, and `Tone::color` is still the one place a meaning becomes a colour. Three of the six map to the tokens C11 predicted (`danger`, `success`, `warning`) and `Muted` to `muted_foreground`, but `Active` maps to `info` rather than `primary` — in the library's dark theme `primary` is near-white, which is right for a filled button and wrong for the word "you" — and `Idle` is `Muted` at 60%, the one distinction the library has no token for. (`Active` was `theme.blue` at first, and that bug is what bought `DESIGN.md`'s rule: no arm of `Tone::color` may name a hue where a role exists.) The catalog was not replaced at that step. It had earned its keep while the old broad `ui.rs` was thirty components with hand-picked hexes; what was left was small enough to see in the app itself, and a preview window that has to be kept honest is a second place for the truth to live.

  *Amended by the Graphite Dark pass.* Two of the claims above have since changed, both in the same direction — what died was the *hand-picked* palette and its preview, not the ideas. `ui/theme.rs` exists again with no per-component hex in it: it names one `ThemeConfig` that fills the library's own slots, so a component still reads `cx.theme()` and never a constant, and `DESIGN.md` is normative for what those slots hold. And the catalog *was* replaced, by the dev-only gallery crate — a story per component (§Tech stack) — because a design system that is written down needs a surface to check it against. The reason this paragraph refused one still stands and has already been paid once: a preview surface is a second place for the truth to live, and its stories drifted from the app's own prompt-row labels inside the pass that shipped them. The debt was settled the only way it can be — by deleting the second place rather than re-syncing it: the two rows that are chrome rather than data are `ui` consts both renderers read, the tone vocabulary is `Tone::ALL`, and the three stories that catalogued prompt parts no screen assembles by hand are gone.

  **The transcript is markdown, and the cheap way is the right way.** Pi's messages are markdown and were rendered as one flat string; they are now `TextView::markdown`. The step arrived with a plan — `push_str` the suffix, because C11 cites incremental reparse as a reason to track `main` — and the source says otherwise. `TextViewState::increment_update` parses **synchronously** for a full replace and **asynchronously on a background task** for an append, and upstream's own comment gives the reason: an async parse leaves the first layout measuring ~0 height, which makes the scrollbar jitter. It also says `set_text` returns early when the text is unchanged. That inverts the plan. A settled message parses exactly once — every later frame passes identical text and does nothing — so the only text that ever reparses is the partial of the turn in flight, bounded by one message and only while it streams. The suffix-diff would have added a prefix-extension assumption about pi's partials that we never verified, to buy back a cost that measurement says is already paid. So the transcript holds no `TextViewState` of its own: `TextView::markdown(id, text)` keeps its state in the window, keyed by element id, and the render stays a pure function of the transcript. The user's own text is *not* markdown — it is what they typed, where a leading `#` is a character rather than a heading. Tool blocks are not markdown either: their bodies are captured output and diffs, already monospaced and already framed, and `.markdown_block_renderer()` is the hook to reconsider them with, not this step. Only what the model wrote gets parsed as what the model wrote. Six grammars join the three from the bootstrap step (rust, python, go, diff, toml, yaml — json comes with the base feature); the full `tree-sitter-languages` set is another 32 grammar crates and is not earned. The library's `TextViewStyle` defaults to the *light* highlight theme with no reference to the app's mode, so the dark one is passed explicitly — one `OnceLock` in `ui/transcript.rs`, not a per-message construction.

  **A dialog's body has to be a view.** `open_dialog` stores a builder on the window's `Root` and re-runs it from the *root view's* render — which for us is inside `Workbench::render`. gpui panics on reading or updating an entity that is mid-update (`cannot read … while it is already being updated`), so a builder that reached for the workbench or the chat to draw its rows would panic the moment the modal opened. Dialog content that needs live state is therefore an entity with its own `Render`, added as a child like any other; only snapshots and weak handles may be captured in the builder itself. That is what turned `FolderPicker` from a plain struct rendered by `impl Workbench` into a view that owns its walk and emits what it needs run, and what made the list modals one shared `Choices` view. The alternative — moving the overlay layers into a wrapper view above `Workbench` so builders run before it is leased — is a smaller diff that works by render *ordering*, and was rejected: it leaves a panic one careless edit away and keeps the god view C12 exists to dismantle.

  **Per-surface modal flags became one ownership rule.** `machine_picker_open` (twice), `ModelControl::open`, and the duplicated picker re-entry flags are deleted. Root itself has one global dialog vector and `close_dialog` pops its top, so it cannot safely arbitrate independent owners: `workbench/modal.rs` owns the stack outright as one `Option<ActiveModal>` — a Pi question, the repo picker, or the forget-machine confirmation — so two flows at once is unrepresentable rather than arbitrated. Pi obligations queue while a user-initiated flow is up; releasing it advances the FIFO front. Retirement closes Root only when the retired obligation is the one on screen, and a callback that does not name the active modal returns false to Root, so no flow can asynchronously pop another's dialog. A model pick still carries the value the user read rather than an index into a refetched list; the prompt-box controls are popovers, not Root dialogs.

  **Then the prompt box's two controls stopped being modals at all.** A control that names its current value and has a caret beside it promises a list *there*, not a dialog in the middle of the window; the model and machine pickers now open in place (`ui::prompt_box_dropdown`), and the repository picker joined them. `choices.rs` is deleted: its last surface was the add-workspace machine step, and picking a repository inside the chat that will run in it means the machine is already known. Two notes for whoever touches it. The dropdown is anchored `BottomLeft`, which opens the list **upward**: the prompt box sits at the bottom of the pane, so a list dropping downward would open past the window edge and be snapped back over the control it belongs to. And `Popover::trigger` demands the library's `Selectable`, which it implements for its own widgets and not for a styled `div` — the prompt box's controls are divs and stay that way, so a local `PlainTrigger` newtype carries the trait without the selected look (the orphan rule allows it precisely because the newtype is ours).

- **C12 — one observable store, not a god view.** `Workbench` owns the `Fleet`, every table, and every request; both event pumps land there and it then reaches *down* into `Chat` imperatively — `chat.update` at twelve sites, one of them inside `render` to borrow a modal element off the child. There is no `cx.observe` anywhere in the crate; the parent re-reads the child by polling `chat.read(cx)` each frame, and both event routers end with an unconditional `cx.notify()`, so every streamed pi token repaints the sidebar, the machine list and the statusbar. The predictable result is duplicated state that goes stale: `ChatTarget.machine_label` is a snapshot taken at open, so a label a provider resolves later never reaches the chat; `Chat.machine_candidates` is a projection of the workspace list that must be re-pushed by hand on every mutation; session status is tracked in two places that can disagree, and `open_session` consults both. *Built.*

  The verdict is a single `Entity<FleetStore>` owning the `Fleet`, the two pumps, and the machine, workspace and session tables. Views observe it instead of being pushed into, and `Chat` reads its label and candidates through it live rather than holding copies. That deletes `refresh_chat_machine_candidates`, the `machine_label` staleness, and most of the twelve update sites; it collapses the four different shapes that loading, error and empty currently take (a proper tri-state enum, a `Pending` plus a hand-written note, a sticky never-cleared `Option<String>`, and `Option`s doing double duty as spinners and guards) into one; and it ends `last_error` accumulating in the statusbar forever by giving errors a notification's lifecycle.

  **What the store passes on, it does not translate.** The store owns both pumps, so every bridge event lands in it first — but a bridge event is mostly pi's, and pi is not translated anywhere in this codebase. The store takes only what is *its* (the fleet takes the link state on the way in; the tables take the session status and the open guard; a `list_sessions` answer it consumes outright) and emits the rest verbatim as `StoreEvent::Bridge`, machine tag and all. There is no second vocabulary to keep in step with pi's. The same rule gives the machines worker's answers to the folder picker untouched, and gives failures — which need a window the store does not have — to the workbench as `StoreEvent::Failed`, where they become notifications instead of a `last_error` that stuck in the statusbar until the next failure replaced it.

  **A view repaints because the store notified, not because a router said so.** Both routers used to end in an unconditional `cx.notify()`, so an event a chat decided changed nothing still redrew the window. The store now notifies from the mutators — a session list, a status, a dot, a workspace — and the two views `cx.observe` it. Note what this does *not* buy: gpui marks a dirty view's ancestors dirty too (`Window::mark_view_dirty`), so a chat repainting still re-runs `Workbench::render` and with it the sidebar. What it does buy is that an event which moved nothing now costs nothing, and that is most of them.

  **A surface routes its own answers.** The twelve `chat.update` sites are gone, and so is the routing layer they were: `with_chat`, `chat_for`, `chat_on`, `abort_machine_flows` and the per-variant dispatch that fed them. `Chat` subscribes to the store and filters `StoreEvent::Bridge` itself — by sid for a session's answers, by machine for the two that have no sid to be found by (an unstarted chat's throwaway `list_models`, and the bridge dying underneath it). A chat knows which sid it renders and which machine it runs on; nothing above it needed to know as well. The workbench keeps exactly one bridge event, `Attached`, because that is the one that has to *build* something and a `Chat` needs a `Window` for its input. This is also what makes a second chat a matter of constructing one rather than of teaching a router about two — the `Option<Entity<Chat>>` is now a choice, not a constraint.

  `Attached` handling runs synchronously inside the store subscriber. Constructing or promoting the chat updates the store's opening catalog, and that is allowed: `cx.emit` only *queues* an effect, which gpui dispatches from `flush_effects` after the emitting `update` has already returned, so during a subscriber callback no entity is leased except the subscriber itself and a subscriber may update its own emitter. `Workbench::defer_attached` — which carried owned machine/sid/entries into `window.defer` — is deleted: it guarded a hazard that does not exist, and the re-lease *inside* the deferred closure was the only thing in it that could ever have panicked. The one property that hop was credited with survives without it, because it never came from the hop: `SubscriberSet::retain` takes the emitter's subscriber list before dispatching and merges back whatever was added during it, so a chat that subscribes while the store is mid-dispatch still cannot observe the event that created it, and is ready for every later one.

  **The chat-state clause is built.** `crates/harvester/src/session_state.rs` is the window-free owner of the one chat's lifecycle, explicit model-list and model-selection states, exit state, request tokens, intents and transcript mutations. `Chat` adapts that state to GPUI and emits the intents; stale and cancelled answers are rejected there. Model payloads and Pi events remain `serde_json::Value` at the boundary, with only picker fields extracted for display.

  **The composition-shell clause is built.** `Workbench` keeps the current chat, constructs a chat where a root `Window` is required, reports store failures, renders content/status, and places `Root`'s dialog and notification layers. `workbench/sidebar.rs` observes `FleetStore`, owns collapse state and sidebar presentation, and emits stable-value intents; the selected session is read from the store (attaching selects, opening an unstarted chat clears) rather than mirrored from the chat. `workbench/modal.rs` is the whole modal layer: one active attachment room per machine, one global obligation FIFO, the folder-picker run and the forget-machine confirmation, all behind one `ActiveModal`, with advancement and retirement subscribed end to end — while empty-room cancellation remains daemon policy. `dialogs.rs` is left with what a Pi question means: which chrome it deserves, what its dismissal answers, and how a click becomes a `DialogAnswer`. A dismissed picker invalidates its pending host work and drops with the modal it owned. The picker itself subscribes to untouched machines-worker answers, resolves hosts through `FleetStore`, and drives `$HOME`/listing/validation without copying fleet state. Store, Attached, modal-release and sidebar continuations all run synchronously in their subscribers; none of them re-enters a leased entity. Exactly one continuation is still deferred, and for an unrelated reason: the modal coordinator's advance to the next Pi obligation, because `gpui-component` pops the dialog stack *after* an answer callback returns, and a synchronous advance would have its own freshly pushed dialog popped instead of the answered one (see `docs/internals/harvester.md` § `workbench/modal.rs`).

  This is why C12 is sequenced *before* the list migration rather than after. `ListDelegate` and `TableDelegate` want to own the data they render; porting lists onto delegates while `Workbench` is still the sole owner would rebuild the hand-pushed-projection problem once per list, and we would pay the migration twice. It also removes the structural reason there can only ever be one chat — `Option<Entity<Chat>>` becomes keyable by sid — which is what makes the docked, tabbed layout in §Post-v1 a later layout change rather than a second rewrite.

- **C13 — absence is only evidence once someone has spoken.** *Built.* A workspace pointing at a deleted VM used to produce nothing at all: `connectable_tracked_machines` skipped the machine because `host_for` failed, the machines section listed the *listing* so the machine had no row, and `Fleet::label` fell back to the key's id half so the workspace row went on reading as healthy. Every dot grey, nothing connecting, no sentence anywhere. The fix is a third source of truth for a machine's state — the provider listing, alongside the probe and the bridge — and the ranking between them: a live bridge outranks the listing, and the listing outranks a probe verdict, because a probe answer about a machine that no longer exists is stale by construction.

  The trap is the ambiguity underneath. "Not in the listing" means *deleted* only if the listing can be believed, and a provider that failed its first `list` produces exactly the same absence. So the worker reports which providers have listed successfully (the key set of its per-provider `ProviderRows` cache already *was* that fact, carried across cycles), the fleet keeps it, and `is_missing` requires it. One broken control plane now reports a broken control plane rather than a deleted fleet. The ghost machines get sidebar rows of their own — the section is the listing plus whatever the client still tracks and can no longer find.

  The dot vocabulary was the other half. `Unknown` and `Reachable` both rendered grey, so "nothing has ever probed this" looked identical to "probed fine, one workspace away from usable". They are now hollow and filled: the state that is not a verdict is drawn as an absence rather than spending a colour the palette does not have (`Tone` has no token for it, and inventing one for a single use is how palettes rot). `ui::Dot` carries the tone and the fill together so `sidebar_stacked_row` still takes one value.

Protocol-level decisions from the same review — the session-swapping denylist (C1), splitting protocol version from build identity (C4), and the dialog obligation and the modal that discharges it (C5) — are recorded in `DAEMON.md` §Decisions on record.

4. Providers: Windows resolution and `secret` field handling are still open; ~~`list` cache tuning~~ — **resolved in the client** (`list` polls every 300s, the SSH probe every 30s, last listing displayed between polls; `PROVIDERS.md` §Open decisions 2). Not contract, by design.

## Tech stack

- **Client**: Rust + git `gpui`/`gpui_platform` from Zed (lockfile commit `08827f9208b4848d62f3faf86ffa15155966d63c`), crate `crates/harvester` — gpui enters no other workspace crate (only the out-of-workspace gallery below), same quarantine rule as clap-in-`harvester-cli`. Layout: the crate carries a small lib target (`lib.rs`: `ui`, `assets`, `shell_bootstrap`) so the app binary and the dev-only component gallery share one component layer and one window bootstrap; everything else is bin-side. The gallery itself is no longer a `[[bin]]` here: it is `crates/harvester-gallery`, a crate with its own `[workspace]` table and lockfile that the root manifest `exclude`s, because its `gpui-mcp-bridge` path dependency does not exist in a clean clone and cargo resolves a member's path deps unconditionally (no feature gate or `cfg` table avoids that — measured). It stays under `crates/` so the filesystem-walking no-comments lint keeps covering it. `main.rs` (manual argv and embedded-musl-daemon resolution via build.rs, plus the `pub use harvester::{assets, ui}` that keeps the app's `crate::ui` paths resolving), `shell_bootstrap.rs` (lib-side: fonts, assets, component/theme policy, app commands, `Root`-wrapped window construction and failure handling, parameterized by title/size/root-view factory; the app-only half — window title, size, and building the `Workbench` root view — is private in `main.rs`), `store.rs` (the `FleetStore`: the fleet, both event pumps and every table, in one entity the views observe — C12), `workbench.rs` (layout and user intent: current chat, content, statusbar, and root-window work) with `workbench/sidebar.rs`, `workbench/machine_presentation.rs` (the one mapping from `MachineState` to dot/pane/statusbar presentation), `workbench/modal.rs` (the single owner of Root's dialog stack: Pi's obligation FIFO, the repo picker and the forget-machine confirmation), and `workbench/picker.rs`, `chat.rs` (one session's conversation, from before it exists until after its pi exits — see C10; it assembles the prompt strip's model, machine, repository and branch state as a plain `ui::PromptStrip` value and renders none of it itself), `dialogs.rs` (which chrome a Pi question deserves — C5), `models.rs` (model domain parsing plus the prompt strip's window-free label policy), `session_state.rs` (window-free chat lifecycle), `workspaces.rs` (the workspace store and labels), and `ui/` (visual responsibility modules: `core.rs` for semantic `Tone`/`Dot` and shared non-colour metrics, `prompt.rs` (the prompt-box primitives plus `prompt_strip`, the whole bottom row rendered from one value struct), `transcript.rs` for item/message/markdown/tool presentation, the reusable tool frame and expansion state, and `shell.rs` for the app frame's chrome — one alignment spine covering sidebar rows, section headers and window chrome; `mod.rs` keeps the small compatibility seam, and every colour is still `cx.theme()`'s). The backbone workers live in `harvester-client-core`, not here: `bridge` (one tokio-runtime thread per machine owning its daemon connection; UI ↔ bridge over reactor-independent tokio mpsc channels; command flows are straight-line futures on a `DaemonClient` pending-map — one `bridge.rs` holding the Command/Event contract, the select loop and the flows, with `bridge/attach_window.rs` kept apart because it is pure, synchronous and unit-testable on its own) and `machines` (provider list, probe worker, and the daemon-free host ops the folder picker and the branch indicator run). Both workers get their runtime from one place, `machines::run_on_tokio_thread`, because the two disagree only about how a failure to build one is reported. `transcript.rs` is the client's model of a conversation — pi's wire shapes across the verified version range (0.83's cumulative `partial` and 0.84's bare deltas both stream; `message_end` is the version-proof fallback), testable without a window; `dialog.rs` does the same for blocking extension questions — the wire shape, one active room per machine, and their global FIFO in one module. Machine identity is client-core's too: `MachineRef::{Local, Provider, AdHoc}` is the one place that decides what a stored machine string means. Above both sits `fleet` — the bridge pool, machine table, probe verdicts and connect policy behind one owner (C3, built). A machine's reachability is one `MachineState`, not a link state beside a probe verdict, so the two cannot disagree; presentation is centralized in `workbench/machine_presentation.rs`. A second frontend gets all of client-core and would still write for itself: the newest-first session list merged across machines, and every rendering decision.
- **harvesterd**: Rust, static musl binary (`x86_64-unknown-linux-musl`), no runtime deps, uploaded over SSH. Layout: `main.rs` (CLI + socket lock + accept + this binary's build fingerprint, plus every path derived from `$HOME`, one owner), `server.rs` (controller: frame/decode/route/encode), `ops.rs` (one function per command), `passthrough.rs` (pi relay + id correlation), `session.rs` (pid table — the only state — plus spawn/pump and the pi launch line, the one place to re-verify on a pi upgrade) with `session/dialog.rs` (the empty-room dialog policy), `fslist.rs` (session listing).
- **Shared**: `harvester-proto` — serde types for the envelope only (pi payloads stay `serde_json::Value` — pass-through by design), plus the canonical framing helpers (`read_frame`/`encode_frame` — LF-only, strip one CR) next to the `LF`/`CR` constants; every frame in daemon and client goes through them.
- **Providers**: any language, one-shot JSON-stdio executables.
